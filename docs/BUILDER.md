# Builder protocol (read fully)

You are the **builder** for ONE piece of FLUX TAG, a browser (Three.js) competitive tag-sport inspired by Counter-Strike 2's polish. A separate, fresh, *harsh* critic will judge your piece by looking at the real running game side-by-side (blind) against real CS2 footage. Your job is to make that critic say "ours feels better". "Good enough" is a fail.

**Read first:** `docs/DESIGN.md`, `docs/ARCHITECTURE.md`, your own `docs/pieces/<id>.md` if it exists (prior rounds), any `docs/requests/<id>-*.md`, and — if this is a repeat round — the critic's last verdict (given in your prompt). Then LOOK at the real CS2 reference for your piece: open images with the Read tool from `reference/cs2/ss_*.jpg` and `reference/cs2/frames/t*_*.jpg` (contact sheets via `python3 tools/sheet.py grid out.png a.jpg b.jpg …` help). If reference files are missing run `tools/fetch_refs.sh`. Use your own deep knowledge of CS2 (movement values, weapon behaviour, HUD, sound design, callouts, economy) — you can also WebSearch/WebFetch for specifics.

**Rules**
1. Only edit files you own (listed in your prompt). Other pieces' files are read-only. Core files are read-only. Need something? Write `docs/requests/…` (see ARCHITECTURE) and code defensively.
2. Shared dev server is already running at http://localhost:5173 (vite HMR; other builders edit at the same time). If the game fails to load because of *another* piece's file, wait 20-30 s and retry; never "fix" their file. Never run `git commit/push/checkout/stash` — the orchestrator commits.
3. Keep your files loadable at all times: make edits in coherent steps, run `npm run smoke` (must pass: no errors, no warnings) before you finish and whenever you've made a big change.
4. Make your piece **inspectable**: expose a `debug` API and `?scene=` gallery scene(s) so a critic can see your piece in isolation, deterministically, via `?test=1&seed=1` + `window.__game.advance(s)`. Write the exact commands/URLs to `docs/pieces/<id>.md` (what exists, how to view each aspect, tuning constants, known gaps). The critic will use these launch instructions, but judges only what they see.
5. **Verify with your own eyes, repeatedly.** Use `node tools/shot.mjs out.png --params "test=1&scene=..." --adv 1` or write scenario scripts with `tools/lib.mjs` (`open()`, `advance()`, `shot()`, `game()`); write outputs under `shots/<id>/`. LOOK at every screenshot (Read tool) and compare to CS2 frames. Do at least 3 self-critique iterations before handing over. For motion/feel, capture frame sequences and tile them with `tools/sheet.py grid`; for numbers (speeds, timings, spread) log telemetry and compare with CS2 known values.
6. Performance matters: no per-frame allocations in hot paths, pool/instance, merge static geometry. Software-GL headless is slow; judge fps by draw calls/tris (`ctx.render.info()`), not wall clock.
7. Procedural only: no external asset downloads (models/textures/audio are generated in code) — except fonts via CSS from Google Fonts are OK for UI. Everything must ship in the repo and run offline-ish from a static build.
8. Harmless tone: light pulses & confetti-shatter, never blood/gore/realistic weapons.
9. Stay within your piece's scope but go DEEP: polish, easing, timing, edge cases, sensible defaults, tiny details CS2 players notice. Think about what makes CS2 feel great in *your* area and reproduce/beat it.
10. Final message to the orchestrator: ≤120 words — what you changed this round, the top remaining weaknesses you know of, and the commands to inspect. No long summaries.
